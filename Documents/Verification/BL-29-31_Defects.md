The measured common-request and submission latency misses are tracked separately as [open performance defect #49](https://github.com/Harsha-Kamaraj/Student-Attendance-Management-System/issues/49). In the initial 50-user, 1,500-request run, all common responses succeeded but only 34.6% completed within 2 seconds; p95 was 4.163 seconds. The initial marking samples were invalid because the HTTPS request harness omitted its Origin/Referer; this was a harness correction, not an application authorization defect.

The full corrected run C kept the same application source and targets, with native CSRF enforcement. All 1,800 measured requests succeeded and peak in-flight concurrency reached 50. The latency defects remain: only 22.4% of 1,500 common responses completed within 2 seconds (p95 3.702 seconds), and the three valid 60-student submissions took 5.780, 4.815 and 3.798 seconds against a 3-second limit. Each submission saved all 60 marks; first-save callbacks produced 60 notifications and 60 captured emails with no repeats on the next saves. Three semester reports passed at no more than 2.998 seconds. Both original and corrected evidence are retained in the execution record.

Monthly availability is an outstanding observation requirement rather than a corrected code defect. Performance defect #49 and the missing monthly observations keep BL-29 and release acceptance open; passing integration checks does not resolve them.
